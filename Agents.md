## Паттерн оркестратора (из Orchestrator Kit)

Используется для feature development, bug fixes, refactoring и общих задач.

### Core Rules

**1. СНАЧАЛА СОБРАТЬ ПОЛНЫЙ КОНТЕКСТ (ОБЯЗАТЕЛЬНО)**
Перед делегированием или реализацией:

- Прочитать существующий код в связанных файлах
- Поискать по кодовой базе похожие паттерны
- Проверить релевантную документацию (спеки, ADR)
- Проверить последние коммиты в смежных областях
- Понять зависимости и точки интеграции

Никогда не делегировать или реализовывать вслепую.

**2. ДЕЛЕГИРОВАТЬ АГЕНТАМ**
Перед делегированием:

- Предоставить полный контекст (code snippets, file paths, patterns, docs)
- Указать точные ожидаемые результаты и критерии валидации

После делегирования (ОБЯЗАТЕЛЬНО):

- ВСЕГДА проверять результаты (читать изменённые файлы, запускать type-check)
- НИКОГДА не пропускать верификацию
- Если некорректно: переделегировать с исправлениями
- Если есть ошибки TypeScript: переделегировать тому же агенту

**3. ВЫПОЛНЯТЬ НАПРЯМУЮ (ТОЛЬКО ДЛЯ МЕЛОЧЕЙ)**
Прямое выполнение только для:

- Установка одной зависимости
- Исправление одной строки (опечатки, очевидные баги)
- Простые импорты
- Минимальные изменения конфигурации

Всё остальное — делегировать.

**4. ОТСЛЕЖИВАТЬ ПРОГРЕСС**

- Создавать todo-лист в начале задачи
- Отмечать in_progress ПЕРЕД началом работы
- Отмечать completed ТОЛЬКО после верификации

**5. EXECUTION PATTERN**

```
FOR EACH TASK:
1. Read task description
2. GATHER FULL CONTEXT (code + docs + patterns + history)
3. Delegate to subagent OR execute directly (trivial only)
4. VERIFY results (read files + run type-check) — NEVER skip
5. Accept/reject loop (re-delegate if needed)
6. Mark task completed + update todo
7. Move to next task
```

**6. LIBRARY-FIRST APPROACH (ОБЯЗАТЕЛЬНО)**
Перед написанием нового кода (>20 строк) ВСЕГДА искать существующие библиотеки:

- Context7: документация кандидатов
- Проверить: >1000 загрузок в неделю, коммиты за последние 6 месяцев, TypeScript/types

**Использовать библиотеку когда**:

- Покрывает >70% требуемой функциональности
- Активно поддерживается
- Разумный размер бандла

**Писать свой код когда**:

- <20 строк простой логики
- Библиотеки заброшены или небезопасны
- Критическая бизнес-логика, требующая полного контроля

**7. HANDLING CONTRADICTIONS**
Если возникают противоречия:

- Собрать контекст, проанализировать паттерны проекта
- Если действительно неоднозначно: спросить пользователя с конкретными вариантами

## Health Workflows (из Orchestrator Kit)

Следующие health-workflow команды запускаются по ключевым словам в запросе:

### Bug Health Check

Ключевые слова: "проверь баги", "bug check", "bug hunt", "найди баги"
Действия:

1. Сканировать код в `src/` на предмет потенциальных багов
2. Категоризировать по приоритету (critical → high → medium → low)
3. Исправить по приоритетам
4. Запустить type-check и тесты после каждого приоритета
5. Финальная верификация
6. Сформировать отчёт

### Security Health Check

Ключевые слова: "проверь безопасность", "security check", "vulnerability scan"
Действия:

1. Сканировать код на уязвимости (инъекции, утечки данных, проблемы аутентификации)
2. Проверить `package.json` на уязвимые зависимости (`npm audit`)
3. Исправить критические и высокие уязвимости
4. Запустить тесты после исправлений
5. Сформировать отчёт

### Dependency Health Check

Ключевые слова: "проверь зависимости", "deps check", "проверь пакеты"
Действия:

1. Запустить `npm audit`
2. Проверить устаревшие пакеты (`npm outdated`)
3. Обновить безопасно (semver-compatible)
4. Запустить тесты после обновлений
5. Сформировать отчёт

### Code Cleanup Check

Ключевые слова: "почисти код", "cleanup", "dead code", "мёртвый код"
Действия:

1. Найти неиспользуемый код (экспорты, переменные, импорты)
2. Удалить мёртвый код безопасно
3. Запустить type-check и тесты
4. Сформировать отчёт

## Завершение сессии (из Orchestrator Kit)

При завершении рабочей сессии выполнить ОБЯЗАТЕЛЬНО:

1. Запустить quality gates (type-check, linter, тесты)
2. Обновить документацию и todo.md
3. Сделать git push (работа не считается завершённой до push)
4. Проверить: `git status` должен показывать "up to date"
5. Предоставить контекст для следующей сессии

**CRITICAL RULES:**

- Работа НЕ завершена пока `git push` не выполнен
- НИКОГДА не останавливаться перед push
- Если push не удался — решить и повторить
