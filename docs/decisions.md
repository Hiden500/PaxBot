# Architecture Decision Records (ADR)

## ADR-001: Network Interception vs OCR

- **Проблема**: Как получать состояние игры.
- **Варианты**: Оптическое распознавание символов (OCR) с экрана или перехват сетевых запросов.
- **Решение**: Выбран перехват сетевых запросов (Network Interception).
- **Причина**: Сетевые ответы содержат чистый JSON, что исключает ошибки распознавания, работает быстрее и надёжнее.

## ADR-002: File-based persistence vs Database

- **Проблема**: Как хранить состояние, историю и стратегию.
- **Варианты**: SQLite, PostgreSQL, MongoDB или простые JSON-файлы.
- **Решение**: Файловая система (File-based persistence).
- **Причина**: ИИ-агенту (кодеру) и LLM (игроку) проще читать и править текстовые файлы. Отсутствуют зависимости базы данных.

## ADR-003: Provider-agnostic LLM abstraction

- **Проблема**: Зависимость только от одного LLM-провайдера (Gemini).
- **Решение**: Создан абстрактный `LLMProvider` с возможностью подключения Gemini, Groq, OpenAI через реестр.
- **Причина**: Гибкость, снижение расходов (возможность переключиться на Groq) и устойчивость к сбоям API.

## ADR-004: Markdown campaign input format

- **Проблема**: JSON сложно писать вручную для сложных стратегических кампаний.
- **Решение**: Использование Markdown в качестве входного формата для кампаний (парсится LLM-билдером в JSON).
- **Причина**: Markdown отлично читается людьми и легко интерпретируется моделями (LLM).

## ADR-005: Session-isolated war-room

- **Проблема**: Пересечение данных при запуске нескольких партий.
- **Решение**: Изолированные сессии `war-room/sessions/<session_id>/`.
- **Причина**: Позволяет параллельно или последовательно играть разные кампании без очистки файлов вручную.
